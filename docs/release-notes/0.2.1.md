# Pipesmith Registry 0.2.1

0.2.1 adds cleanup policies with a preview, and three task kinds that clean up and compact stores. Updates come from GitHub releases, and a release check feeds a new Updates screen. Each hosted repository can write into a blob store of its own. The REST API adds named tokens, a change of the own password and task settings. The source repository gains browser checks of the interface. `state.sqlite` moves to schema 6 and `catalog.sqlite` to version 6 (see Upgrade). The first move from 0.2.0 goes through `update <folder>`. Writes and requests to remotes stay off until you turn them on.

## Fixed

- A blob store that is empty and has no rows in the index shows as available, with 0 blobs and its free space. 0.2.0 showed it as unavailable. A store is unavailable when its folder is missing or cannot be read. It is also unavailable when it is empty while the index holds rows of it, as on a disk that is not mounted.
- The page of a blob store is drawn at once. 0.2.0 walked every properties file of the store on each request for the row Marked for deletion, and the page stayed blank on a large store. The row now comes from a count kept in `catalog.sqlite` (see Added).

## Added

- Cleanup: `GET /api/cleanup-policies` lists the cleanup policies by name, and `GET /api/cleanup-policies/{name}` returns one policy or `404`. Each policy shows the criteria `lastBlobUpdatedDays` and `lastDownloadedDays`, `null` when not set, and in `usedBy` the repositories that apply it. Reading needs `nexus:settings:read`.
- Cleanup: `POST /api/cleanup-policies` creates a policy (`201`), `PUT /api/cleanup-policies/{name}` saves it (`204`) and `DELETE /api/cleanup-policies/{name}` deletes it (`204`). These need `nexus:settings:update`. The body is `{name, format, notes, criteria}` and holds at most 65,536 bytes, otherwise the answer is `413`. The format is `*`, `maven2`, `npm`, `docker` or `raw`. Notes hold at most 400 characters (`400` with `notes-bound`). At least one criterion must be a whole number of days, 1 or more (`400` with `criteria-missing`). A name that exists answers `409`, and so does the delete of a policy that a repository applies, with every such repository named.
- Cleanup: a save never refuses a value the stored policy already holds, including an imported format or criterion. A stored criterion that this server does not know stays when the body leaves it out, and the policy then does not run. A policy saved through REST counts as made on this server, so a later import keeps it.
- Cleanup: `POST /api/cleanup-policies/preview` takes `{policy, repository}` and lists what a run of the policy would remove from that repository, without removing or writing anything. The answer has at most 100 items, sorted by path, with `total` and `truncated`. The preview needs `nexus:settings:read` and the browse permission of the repository. A repository the caller may not browse answers as one that does not exist. One preview runs at a time per server, and a second one gets `429` with `Retry-After: 5`. The preview also runs while the server is frozen. Its audit line has the action `cleanup-policies.preview`, also when the preview is refused.
- Cleanup: while the server is frozen, every create, save and delete of a policy answers `503` with the reason of the freeze. This includes a save or delete of a policy named `preview`.
- Cleanup: three task kinds run. `repository.cleanup` runs every cleanup policy over the repositories that apply it. It takes an optional `repositoryName`, where `*` or no value means all repositories. `blobstore.compact` removes the files of blobs whose delete mark is old enough. It reads `blobStoreName`, or `blobstoreName` when that is absent. `repository.maven.remove-snapshots` keeps `minimumRetained` builds of each snapshot version and removes older ones by the time in the file name.
- Cleanup: a run counts its result in the task message, for example "cleanup policies: N runs, N refused, N selected, N removed, N kept, N skipped". A pair of policy and repository of another format is counted as refused and the run goes on. Any other failure ends the run.
- Cleanup: a Docker blob is removed only when no manifest names it, and the manifests are read again before the first blob is removed. A blob that no manifest names joins a run only when it is older than 6 hours, because a push writes its layers before the manifest. A child manifest that a remaining list or index names stays. A compaction also removes a loose bytes file left by a stop between the two removals, and the catalog row of the removed blob.
- Cleanup: `catalog.sqlite` records the time of the last download of an asset. The server writes these times in batches every 10 seconds. It replaces a stored time only when that time is more than 12 hours old, so the recorded time can be up to 12 hours older than the last download. A policy by usage reads it.
- Updates: a release source for GitHub releases. Drafts and prereleases are left out, and a release counts as complete by its asset list. Signature, checksum and SBOM are checked before the downloaded binary runs for `version`, as in 0.2.0.
- Updates: without the key `channel` in `update.json`, `update --fetch` and the release check ask the GitHub releases of the project. The key also takes `{"github": "owner/repo", "api": "<address>"}`.
- Updates: `update --fetch --install [--version V|latest]` fetches and then switches, with the same way back as `update --switch`. It takes over a switch that the timer marked as due, and marks a failed switch so the timer does not try that release again.
- Updates: the key `window` in `update.json`, written `"HH:MM-HH:MM"` in the local time of the host, limits the automatic switch. It must contain minutes 0 to 10 of some hour, because the timer starts there. The automatic update itself is the key `scheduled_switch` of 0.2.0.
- Updates: the timer of the release runs hourly with a random delay of up to 10 minutes. The result of its last run is in `releases/scheduled.json`: `nothing`, `staged`, `waiting`, `switched`, `back` or `failed`. The result `back` means the way back ended with the earlier release healthy. Lines of `releases/history.jsonl` from a scheduled run carry `"auto": true`.
- Updates: a release check. While it runs from an install root, `serve` asks the source every `check_hours` hours (default 6, 0 to 168, 0 turns it off) and keeps the answer in `<data>/updates/releases.json`. `POST /api/updates/check` runs a check on demand. It needs the permission `nexus:atlas:read` and is allowed while the server is frozen. Two checks are at least 5 minutes apart, and no check runs while the source limits requests. A check ends after 2 minutes.
- Updates: `GET /api/updates` adds the version, the state of the source, the newest release and the list of releases. It also returns the automatic update (enabled, window, timer, last run), the last update and the 50 newest lines of the history.
- Updates: the screen Updates shows the installed version, the newest release and whether an update is available, the button Check for new version, and the last and next check. It shows the notes of the newest release with older notes folded, the history, and a panel for the automatic update. It notes when the last automatic update went back. Release notes are drawn as text, and only http and https links are active.
- Updates: the GitHub API allows 60 requests per hour without a token (header `x-ratelimit-limit`, read with curl on 2026-11-21). A request past the limit stops with the reset time.
- Stores: a hosted repository writes into the blob store it names. When you create a hosted repository, the form and the REST body pick `local-write` or a store created on this server, or create a new store in the same change. The store of a hosted repository is fixed after the create. Stores of the old product stay read only, and proxies stay on `local-write`.
- Stores: each store has one writer, opened on first use. Marks, space checks, scans, the repair at start, Docker upload sessions and npm spools work in the store of the repository. A start with writes off attaches created stores read only.
- Stores: `GET /service/rest/v1/blobstores` has the new field `writable`.
- Stores: the count of marked blobs of a store lives in the table `store_marks` of `catalog.sqlite`. A scan writes it while it walks the store. A delete mark adds 1 and the size of the blob, and a compaction takes them off, each time right after the change. `GET /api/blob-stores/{name}/deleted` answers from the row at once with `blobCount`, `bytes`, `counting` and `countedAt`. For a store whose folder does not exist, the answer is `200` with `reason` and no count, and the page shows Not counted with the reason.
- Stores: a store of the old product without a row takes its first count from `<data>/marked-counts.json` when the entry names the same root as the store and `unreadable` is 0. The server imports the entry without a walk and logs one line. Without such an entry, the first request of the page starts one background walk of the store, the page shows Counting, and the result is kept as the row. No walk runs at a start and none repeats later. A store of this server never takes its count from the file.
- Tokens: `GET /api/tokens` lists the tokens of the signed in user, and `POST /api/tokens` issues a token with a name. The secret is shown once at issue. `DELETE /api/tokens/{id}` revokes a token, and a revoke takes effect at once, also in the credential cache. The permission `nexus:users:update` allows listing and revoking the tokens of another user. A revoke of the token of another user without that permission answers `404`.
- Account: `PUT /api/account` changes the own account, and `POST /api/account/password` changes the own password. The change compares the stored form and writes the new one in one step. A failed compare answers `400` at `currentPassword`. A password change ends every session of the user, the current one too.
- Tasks: `GET /api/task-types` lists the kinds, and task settings can be read, created, saved and deleted under `/api/tasks`. A save is checked by the rules that refuse a task at load. A task id is 16 lowercase hex characters, a body above 65,536 bytes answers `413`, and a delete keeps the runs and secret files of the task. A saved imported task becomes a local one, and a later import keeps the saved task.
- Interface checks: `tests/ui/run.sh` in the source repository opens the screens of the interface in the built binary. It does this as the roles admin, reader, nobody and signed out, in light and dark at 1280 and 390 pixels. A run has 436 rows. The runner repeats it three times and reports a row that differs as a flake. A row that fails belongs to a class in `tests/ui/classes.json`, and a failed row without a class fails the runner. In the last run on the development machine (2026-11-21), 420 rows passed and 16 failed, all in a class (the two Interface entries under Limits). The three runs took 311.6 s in all.
- Documentation: the OpenAPI document and the manual describe the new routes. The manual has a section Created Stores with the REST body and the refusals, and the sections Release Check and Updates Screen.

## Changed

- `catalog.sqlite` moves to version 6 and `state.sqlite` to schema 6 (see Upgrade). Version 5 of the catalog stores the time the file was built, and version 6 adds the table `store_marks`. Schema 6 of the state file adds the column `name` to `tokens` and a unique index over user, source, kind and a name that is not empty.
- A catalog file of an earlier version takes the time of its migration as its build time. A policy by usage reads that time as the earliest download, so after the upgrade it selects nothing until the days of its criterion have passed.
- The refusals `store-read-only` and `store-fixed` (both `400`) are new. A hosted repository that names a store of the old product is refused with `store-read-only`. A save that would move a hosted repository to another store is refused with `store-fixed`.
- `repos write-settings --write-store` takes only the store the repository writes into.
- The listing of blob stores does not name `local-write`. The repository form adds it.
- The bound of 20 tokens of a kind revokes only unnamed tokens, such as npm logins. A 21st named token of a kind answers `409` with `token-limit`.
- Token and account writes need a session or the password. A subject that signed in with an npm or user token gets `403` on them, and can still list its tokens.
- The two texts of the blob store pages name both causes of an unavailable store.
- `serve` writes the work files of npm spools and Docker sessions into the store of the repository, not into `local-write`.
- The update timer of the release runs hourly with a random delay of up to 10 minutes. In 0.2.0 it ran daily with a delay of up to 1 hour.

## Upgrade

- 0.2.0 refuses the GitHub form of `channel`, so it cannot fetch 0.2.1. The first move to 0.2.1 goes through `update <folder>` with the release files, as under Verify. Every later update can fetch.
- `update` refuses to run while a copy `<file>.v<n>` or `<file>.failed` is in the data directory. Move the copies of the 0.2.0 migration away before `update` installs 0.2.1.
- Make a backup of `state.sqlite` and `catalog.sqlite` before the first start of 0.2.1, with the server stopped. The first command that opens `state.sqlite` migrates it to schema 6 and writes `state.sqlite.v5` first, with mode 0600. `catalog.sqlite` migrates to version 6 at the next start. Its copy `catalog.sqlite.v<n>` is written only when the disk has twice the size of the file free, so a backup of your own is the safe way back.
- A binary of 0.2.0 refuses `catalog.sqlite` of version 5 and 6. The way back to 0.2.0 therefore needs the backups:
  1. Stop the server of 0.2.1.
  2. Move `state.sqlite`, `state.sqlite-wal` and `state.sqlite-shm` out of the data directory, and put the backup of `state.sqlite` or `state.sqlite.v5` in their place.
  3. Move `catalog.sqlite` with its `-wal` and `-shm` files out of the data directory and put your backup in its place. Without a backup, the next `scan` of 0.2.0 writes the file again.
  4. Put the 0.2.0 binary back and start it.
- The way back loses the changes made after the upgrade, such as tokens with a name and tasks and cleanup policies saved through REST. The counts of marked blobs are lost too.
- The update timer of the release changed to hourly (see Changed). The update service names the data directory `/var/lib/pipesmith-registry`, as in 0.2.0. When your data directory is another one, set `Environment=PIPESMITH_REGISTRY_DATA` and `ReadWritePaths` to your data directory and the install root in the unit.
- A store of the old product shows its marked count only after one count. Before the first start, put `marked-counts.json` into the data directory, or run `scan <store>` for each store once. Otherwise the first request of the page of each store starts one background walk.
- Stores created on this server keep their files below the path of their record. A hosted repository created before 0.2.1 keeps writing to `local-write`.
- Writes stay off unless `serve --writes`, `PIPESMITH_REGISTRY_WRITES` or `"writes": true` turn them on. Requests to remotes stay off unless `serve --upstream`, `PIPESMITH_REGISTRY_UPSTREAM` or `"upstream": true` turn them on.

## Limits

- Cleanup: a preview reads every asset of the repository. On the development machine, one preview over 100,000 assets took 309 ms and raised the heap in use from 33 MiB to 214 MiB (one run of `TestMeasureAPreviewOf100000Assets`, 2026-11-21). Larger repositories are not measured.
- Cleanup: the answers carry no field that says whether a policy can run. A criterion this server does not know shows in `criteria`, and a run and a preview refuse the policy. An imported format outside the five is shown and kept as stored, and a run and a preview refuse it.
- Cleanup: a snapshot retention counts builds per snapshot version (group, artifact, base version), not per artifact.
- Cleanup: the Docker grace of 6 hours is fixed and is not a property of a policy.
- Cleanup: a download that the server answers while it stops is not recorded.
- Cleanup: the manual has no chapter on cleanup policies beyond the OpenAPI pages, and none on the three new task kinds or on compaction.
- Updates: `update --fetch` has run against a stub of the GitHub API and against the unauthenticated list of the real API. It has not yet run with a complete signed release from GitHub.
- Updates: `update` and `rollback` need systemd and do not apply to a container. The release check of `serve` runs only from an install root.
- Updates: a window must contain minutes 0 to 10 of some hour. The timer does not try again a release whose scheduled switch failed.
- Stores: the command `scan` does not scan created stores. `serve` scans them at its start with writes or upstream on. An index rebuilt with `scan` alone therefore serves their files only after the next `serve` with writes on.
- Stores: a store that was never scanned and whose disk is not mounted shows as available and empty. After `store add`, scan each store once.
- Stores: a write that reads the state between the commit of a store delete and the update of its view can open the writer of the deleted store again. It closes at the next restart, and no data is lost.
- Stores: a stop of the server ends the count walk of a store without waiting for it. A walk ends at its next check, after at most 1024 files.
- Stores: a proxy stays on `local-write` and cannot pick a store.
- Tokens: the CLI `token issue` issues unnamed tokens, which count to the bound of 20.
- Account: the refusal for the account of a directory user is proven in unit tests and not against a signed in directory user.
- Interface: the role editor asks `GET /service/rest/v1/security/roles?source=LDAP`, which the server answers with `501`, and the browser logs a console error.
- Interface: for a repository that the subject may not view, the tree and the viewer show "This repository does not exist" in place of the screen for missing access.

## Verify

Compare the fingerprint of `cosign.pub` with this one before you trust the key:

```bash
openssl pkey -pubin -in cosign.pub -outform DER | sha256sum
```

The SHA-256 of the key of 0.2.1 is the same as for 0.2.0:

```text
2ca9a77b196bab0d81a95d464778f9989c08da84f6ca2d1327fd8987f47bb595
```

Then check the signature over `SHA256SUMS` and the files against it:

```bash
cosign verify-blob --key cosign.pub --bundle SHA256SUMS.sigstore.json --insecure-ignore-tlog SHA256SUMS
sha256sum --check --ignore-missing SHA256SUMS
```

The bundle has no transparency log entry, so `cosign verify-blob` needs `--insecure-ignore-tlog`. The fingerprint above takes the place of the log.
